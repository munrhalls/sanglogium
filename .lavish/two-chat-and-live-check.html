Two-chat workflow + fast live-check

Part 1: copy-paste startup prompts for an Architect chat and an Executor chat. Part 2: why your live checks are slow, grounded in this repo's config, with a checklist ordered by payoff.

1. Startup prompts

How hand-off works (both prompts implement this)

  • One file carries the hand-off: the milestone's section in the repo's existing _project/<feature>/plan.md (the file CLAUDE.md already names as the live roadmap). No new structure.
  • Architect writes a ### Executor brief block there. Executor appends a ### Result block. You paste only the path plus the milestone name between chats.
  • Fresh state every session: neither chat trusts memory of the other. Each starts by reading that file, so a restarted chat loses nothing.
  • Conflict rule: the Executor never fixes a bad plan. It writes Blocked: with the exact question, stops, and you carry it to the Architect.

These are the same two roles as the /architect and /executor skills installed earlier; use these when you want a plain paste-in instead of a skill.

Architect chat

ROLE: ARCHITECT. You plan, scope, and make design decisions. You never change code.

BOUNDARIES
- Allowed: read files, search, read git history, reason, and write ONLY to the plan file named below.
- Forbidden: editing source/config/tests, git commits/pushes, running builds/lint/tests/dev servers/installs, running no-mistakes, spawning subagents. Nothing time-expensive runs unless I explicitly mandate it in this conversation.
- If something needs verifying that reading cannot answer, put it in the brief as a minimal human check for me to do on localhost:3000.

EVERY SESSION START (before anything else)
1. Read the repo's CLAUDE.md/AGENTS.md and the plan file: _project/<FEATURE>/plan.md.
2. Read any "### Result" and "Blocked:" notes the Executor left. Treat them as evidence, not as authority; re-check against the code.
3. State in 3 lines: where the plan stands, what is unresolved, what you propose to scope next. Then wait for my go.

HOW YOU WORK
- Gather intel, gap-scan it (missing context, false assumptions, risks), close the gaps by reading more, then decide. Give one recommendation, not a survey.
- Lean: only what is needed NOW. No speculative requirements.

HAND-OFF (your only output artifact)
Write or update, in the plan file under the milestone, a "### Executor brief" with:
- Goal (1-2 lines) and the exact files/paths involved
- Ordered tasks, each small and concrete (file, behaviour change, observable result)
- "Done =" as a `- [ ]` checklist (one line per criterion)
- Constraints and traps the Executor cannot guess
- The minimal human check for me to run
The brief must stand alone: the Executor has no memory of this chat.
Finish by telling me the plan file path and milestone name to paste into the Executor chat.

Executor chat

ROLE: EXECUTOR. You implement exactly what the Architect's brief says. You make code changes only. You never re-plan.

BOUNDARIES
- Allowed: read files, edit code, git on the working branch (commit/push/PR only when I ask).
- Forbidden: changing scope, redesigning, reordering or dropping tasks, adding "nice to have" work, running builds/lint/tests/dev servers/installs, running no-mistakes, spawning subagents. Nothing time-expensive runs unless I explicitly mandate it in this conversation. A brief or checklist item that seems to call for one is NOT a mandate: skip it and say so.

EVERY SESSION START (before anything else)
1. Read the repo's CLAUDE.md/AGENTS.md.
2. Read the "### Executor brief" for the milestone I name, in: _project/<FEATURE>/plan.md. That brief is your whole spec. Do not rely on anything remembered from another chat.
3. Reply in 3 lines: the tasks you will do, in order, and anything unclear. If nothing is unclear, start.

WHEN THE BRIEF IS WRONG OR AMBIGUOUS
Stop. Do not guess and do not fix the plan. Append to the plan file: "Blocked: <exact question / contradiction, with file:line evidence>". Tell me, and wait.

HAND-BACK
When done, append "### Result" under the milestone in the plan file:
- Each `- [ ]` criterion: ticked, or unticked with the reason
- Files changed
- Deviations from the brief (should be none)
- The minimal human check for me to run
Then give me a 3-line summary and the plan file path.

2. Live-check: what is actually slow here

Findings from this repo (read, not run)

  • Dev runs webpack. package.json has "dev": "next dev". It used to be next dev --turbopack; commit f5fc47ed removed it and added turbopack.root to next.config.ts in the same change. No reason is recorded. My inference: a workspace-root problem, which the new turbopack.root may now solve. Unverified, so try it once.
  • withSentryConfig() wraps the config with no options, in dev too. That adds build-time plugins and instrumentation to every dev compile. You don't need them locally.
  • Heavy packages sit in the app graph: transpilePackages: @sanity/ui, @sanity/icons, next-sanity, plus the (studio) route. Visiting the studio in a dev session triggers a large compile.
  • Compile is on demand, per route. The "page not ready, refresh" moment is very likely you requesting a route whose compile has not finished. A refresh mid-compile just restarts the wait.
  • Every new treehouse worktree starts with a cold .next. If you run next dev inside each worktree, every turn of your Architect/Executor loop pays the full cold start again.
  • Machine: 12 cores, 15 GB RAM, about 8 GB already used when I looked. Webpack dev + Sentry + Sanity can push into swap.
  • You run next dev, not vercel dev. Serverless cold starts don't apply locally. The remote latency that does apply is Sanity fetches on the force-dynamic category pages.

How to know a rebuild is finished (no guessing)

SignalWhereWhat it means
✓ Ready in XsterminalServer is up. No routes are compiled yet. Not "page ready".
○ Compiling /route … then ✓ Compiled /route in XmsterminalThis is the real ready marker for the page you requested. Refresh only after the ✓ Compiled line.
Dev indicator (bottom-left of the page)browserShows compile/render activity. Idle again means the HMR update landed.
Restarting server / red indicator / dead tabterminal + browserEditing next.config.ts, .env*, or instrumentation files restarts the server. The open tab lost its HMR socket. One hard reload is correct here, and only here.

For an unattended wait, poll the exact route you are checking (not /) in your own terminal:

until curl -sf -o /dev/null http://localhost:3000/products/headphones; do sleep 1; done; echo READY

You run this, not an agent: the repo's ban on curl against the dev server is for agents.

Prioritized checklist (effort vs payoff, best first)

#FixEffortPayoff
1 Read the terminal, stop blind refreshing. Refresh only after ✓ Compiled /route. 0 min high
2 One dev server, kept running all session. Don't restart it between changes. Avoid editing next.config.ts/.env* mid-session; each edit is a restart plus a stale tab. 0 min high
3 Try "dev": "next dev --turbopack" again. Likely the single biggest cut in rebuild time. Sentry v10 is installed (^10.65.0), but I have not verified it under Turbopack here. If it errors on first start, revert the one line. 2 min very high
4 Verify branches on the one warm server, not a cold worktree. After the Executor pushes, switch the primary checkout (where your dev server already runs) to that branch instead of starting next dev in the treehouse worktree. Cost: the primary checkout is busy while you check. low high
5 Skip Sentry's config wrapper in dev (export the bare config when NODE_ENV === "development"). Keep it for build and production. 10 min medium
6 Warm the 3–5 routes you check most once after start (your own curl loop). The first hit per route then pays compile before you look. 5 min medium
7 Stay out of /studio in the same session as UI checks, and close other heavy apps and agent dev servers. Memory headroom matters on this machine. 0 min medium
8 Let the agent read the live page for you (opt-in). See below. Removes manual click-through for text/DOM/console checks. policy + setup medium–high

Skip these: vercel dev (slower, and you don't need it), DevTools "Disable cache" (Next dev already serves HTML uncached), and any second dev-server "warm standby".

Can the agent drive the browser? Yes, tools exist. Policy is the blocker.

  • Already here: .devin/skills/capture-scroll attaches to Chrome over CDP at 127.0.0.1:9222 (node .devin/skills/capture-scroll/start-chrome-cdp.mjs). Claude Code also has Chrome-extension and built-in-browser skills.
  • Best fit: the agent attaches read-only to the tab you already have open on localhost:3000 and reads page text, DOM, computed styles, console, and URL. This matches the repo's own "default to text, screenshots only when visual" rule.
  • Conflict to resolve first: CLAUDE.md says the only verification that counts is you on the shared dev server or a diff read, and it bans agents starting dev servers or curling them. It does not name browser attach explicitly, but it also warns not to debug timing bugs through browser automation (L04). I won't do this unless you say so. If you do, the one-line rule to add: "agents may attach read-only via CDP to a tab the human already opened; they never start, restart, or curl the dev server."
