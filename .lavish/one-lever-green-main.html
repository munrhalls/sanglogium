The one lever: let a machine say “green” before anything reaches main

Your question: what is the one easy thing that makes the rest of shipping at 8+/10 easier or irrelevant? Answer first, then the evidence from today’s history, the first-principles argument, eight alternatives, and what I could not verify. Read-only analysis: nothing in the repo was changed.

The answer

Make GitHub — not you, not your laptop — decide whether a change may enter main.

Concretely: one required check named verify (tsc --noEmit) on every PR and every push to main. About 15 lines of YAML and one repository setting. The repo is public, so runners and branch protection are free.

Takes work off the bottleneck

Your attention is the only scarce resource in the loop. Type and build errors are compiler work, not review work.

Gives Devin an oracle

A remote check costs your laptop nothing, so “agents never run checks locally” stops costing quality.

Makes every later gain one line

Lint, unit tests, a width check, a preview URL: each becomes one added line that runs forever, not one more box you re-tick by hand.

First principles

  1. 1. Throughput is set by the slowest stage.

    Architect and Devin are cheap and parallel (three worktrees ran at once). The one serial stage is your attention plus one shared dev server. More executors only add unmerged inventory: 19 local branches, a live-check scratch branch, PRs waiting up to 3 h. So there are three ways to ship faster: take work off you, stop rework re-entering, shorten feedback. Nothing else moves the ceiling.

  2. 2. A person should verify only what a machine cannot.

    Types, imports and builds are machine work; many size, overflow and ARIA assertions are too. Taste, hierarchy and “does this solve the product problem” are yours. Today’s failed deploys: 4 of 4 were type errors, the class you are worst placed to catch by eye.

  3. 3. An agent with no oracle cannot converge, so a person becomes its oracle.

    Your ban on local checks removes Devin’s only oracle to protect a laptop that already wedges (swap 1.7/2 GB and a 2.8 GB next-server, per .lavish/dev-server-wedge.html). A remote check costs the laptop nothing, so the ban’s reason does not apply to it.

  4. 4. A defect’s cost grows with the delay before it is found.

    At PR time: minutes, author’s context still loaded, a ~20 s check. At deploy time: 11 days later, 83 commits on top, and three 5-minute builds to see three errors one at a time.

  5. 5. Verification must scale with production.

    N executors make N PRs. Your review time does not scale with N; a GitHub runner does, in parallel, for free on a public repo.

Your open question: PR per turn, or one at the end?

Per turn. Defect cost grows with batch size times detection delay, so smaller batches fail cheaper and sooner, and every merged PR is a checkpoint you can revert to. The wrinkle is not the cadence but the branch lifetime: a branch reused after its PR merged is diverged from main (same mechanism as today’s failed pull on live-check). Reset the axis branch to origin/main at each turn start, or use a fresh branch per turn. Your rule, your call.
