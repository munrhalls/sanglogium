Dev server wedge: prevent first, recover fast

Evidence read from this machine while your dev server was running, then the prevention table, then the recovery path. I did not run the dev server or the new script.

What I measured (10 minutes after a fresh start)

  • Swap 1.7 GB of 2 GB used, only 329 MB free. RAM: 15.6 GB total, 8.9 GB used. Once swap fills, a Node process stops responding while it thrashes. This matches "unresponsive, not crashed".
  • next-server RSS 2.78 GB at 10 minutes uptime, on webpack with Sentry wrapped in.
  • File watchers: max_user_watches=135755. Not a problem unless you see a watcher error (row 4).
  • One next dev, no overlap right now. .next is 478 MB.

So memory pressure is the prime suspect. Corrupted .next is more likely a consequence (killed mid-cache-write) than the cause.

1. Prevention (highest payoff first)

#CauseDetect earlyPrevent
1 Memory / swap exhaustion devctl.sh watch warns at server > 4 GB or swap > 90%. Done in the repo: dev now runs next dev --turbopack; Sentry's wrapper is skipped in dev. Both cut dev memory (my expectation, not measured).
You run (needs sudo), grow swap 2 to 8 GB: 
sudo swapoff /swapfile && sudo fallocate -l 8G /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
Optional, kill a runaway instead of freezing the desktop: sudo apt install earlyoom
2 Corrupt / stale .next after a hard kill, dependency change, config edit, or big branch switch Terminal errors: Cannot find module, ENOENT … .next/server, manifest errors, Caching failed. Stop with Ctrl-C, never kill -9 first (TERM lets the cache flush; devctl.sh restart uses TERM, then -9 only after 3 s). Restart the server after npm install, editing next.config.ts/.env*, or a git switch that changes package-lock.json.
3 Overlapping dev processes on the same checkout pgrep -af "next dev" shows more than one; port 3000 "already in use". One server per checkout. The repo ban already stops agents starting one. devctl.sh restart kills by port and by this repo's path first, so a stray process can't survive a recovery.
4 File-watcher overflow Terminal shows ENOSPC: System limit for number of file watchers reached or EMFILE. Only if it appears: 
echo fs.inotify.max_user_watches=524288 | sudo tee /etc/sysctl.d/40-inotify.conf && sudo sysctl --system
5 Heavy one-off routes (/studio, Sanity packages) Memory jumps right after visiting /studio. Don't open /studio in the UI-checking session. Restart after using it.

2. Fast-path recovery

New file: scripts/devctl.sh (syntax-checked with bash -n only, never run). One-time alias for your shell:

alias dr='~/work/sanglogium/scripts/devctl.sh restart'
alias drc='~/work/sanglogium/scripts/devctl.sh restart --clean'
alias drw='~/work/sanglogium/scripts/devctl.sh watch'
StepCommandUse when
1drDefault. Kill and start, keep .next. Most wedges are a memory-thrashed process, and this fixes them.
2drcSame error after step 1 (module/manifest/ENOENT). Removes build output but keeps .next/cache, so the restart stays fast.
3devctl.sh restart --nukeLast resort: rm -rf .next. Slowest, and rarely needed.

Is rm -rf .next necessary? Usually not. It is what makes your recovery take minutes, because it also throws away the compile cache. Escalate only when a plain restart repeats the same error.

Detecting "wedged" without clicking around

Run drw in a second terminal tab. Every 10 s it fetches /robots.txt (tiny route) with an 8 s timeout. Two failures in a row, or server > 4 GB, or swap > 90%, prints a line and raises a desktop notification (notify-send). It only warns; it never restarts on its own.

Your own curl: the repo's curl ban is for agents. Note the first probe after a cold start includes compile time, so one early failure is normal.
