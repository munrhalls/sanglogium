## 1. PCI-DSS SAQ A — scope for a Stripe Elements + PaymentIntents integration

### Sources
- PCI Security Standards Council, *PCI DSS v4.0.1 Self-Assessment Questionnaire A* (SAQ A r1)
- PCI SSC, *FAQ Clarifies New SAQ A Eligibility Criteria for E-Commerce Merchants* (FAQ 1588, 28 Feb 2025)
- Stripe, *A guide to PCI compliance* (https://stripe.com/guides/pci-compliance)

### Applicability to this integration
The current architecture uses:
- **Stripe Elements** (`PaymentElement`, `ExpressCheckoutElement`) mounted in the client for card / wallet entry.
- **Stripe PaymentIntents** created/updated on the server with `clientSecret` returned to the client.
- Card data is collected by Stripe-hosted fields and sent directly to Stripe; the merchant server does **not** receive raw PAN, CVV, or track data.

This is the textbook SAQ A pattern. SAQ A eligibility requires all of the following for the payment channel:

1. Card-not-present (e-commerce) transactions only.
2. All account-data processing is outsourced to a PCI-DSS-compliant third-party service provider / payment processor (Stripe is PCI Service Provider Level 1).
3. The merchant does **not** electronically store, process, or transmit any account data on its systems or premises.
4. The merchant has reviewed the TPSP's Attestation of Compliance and confirmed PCI-DSS compliance for the services used.
5. Any account data retained is only on paper (not applicable here — none is retained).
6. For e-commerce channels specifically: **all payment-page/form elements delivered to the customer’s browser must originate only and directly from the PCI-DSS-compliant TPSP/payment processor** (e.g., Stripe iframes).

### New PCI DSS v4.0.1 consideration — script-attack susceptibility
FAQ 1588 clarifies the new SAQ A r1 criterion:

> *“The merchant has confirmed that their site is not susceptible to attacks from scripts that could affect the merchant’s e-commerce system(s).”*

For an embedded payment form (iframe / Stripe Elements), the merchant can confirm this by either:
- Implementing controls such as those in PCI-DSS Requirements 6.4.3 and 11.6.1 (e.g., CSP, SRI, script-integrity monitoring, subresource integrity) to protect the payment page from scripts targeting account data; or
- Obtaining confirmation from the PCI-DSS-compliant TPSP (Stripe) that, when implemented per their instructions, the solution includes techniques that protect the merchant payment page from script attacks.

**Calibration against this repo:** `CHECKOUT-SYNOPSIS.md` §3.4 confirms Stripe Elements / PaymentIntents are used, but it does **not** state how the merchant page protects against malicious scripts injected into the merchant origin (CSP, SRI, script-integrity monitoring, etc.). This is a gap to record for the audit stage: the page should either document a Stripe-provided assurance or a merchant-side control that satisfies the v4.0.1 script-attack criterion.

### SAQ conclusion
If the integration remains “card data never touches our server,” continues to use Stripe Elements/PaymentIntents exactly as documented, and does not begin writing custom code that handles raw card information, the appropriate PCI validation route for a Level 2–4 merchant is most likely **SAQ A**. Any deviation (custom card input, server-side card handling, etc.) would move the merchant out of SAQ A and into SAQ A-EP or SAQ D territory.

## 2. OWASP Session Management Cheat Sheet — checkout session controls

### Source
- OWASP Cheat Sheet Series, *Session Management Cheat Sheet* (https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### Findings calibrated to the checkout session (`lib/session.ts` as described in `CHECKOUT-SYNOPSIS.md` §4.1)

| OWASP guidance | Current implementation (per synopsis) | Gap / note |
|---|---|---|
| Session IDs should have ≥ 64 bits of entropy and be generated by a CSPRNG. | `checkoutSessionId` is generated client-side as `chk_{timestamp}_{random}` then stored. | **Potential gap:** Client-side generation of the trace ID is acceptable as a correlation ID, but it should not be treated as a cryptographically strong session ID if it is also used for authorization. The actual cookie is encrypted by `iron-session`; the entropy of the *cookie value* is determined by `iron-session`. |
| `Secure` attribute mandatory for HTTPS-only cookie transmission. | `secure` in production (`secure (prod)`). | **OK for prod.** Ensure it is enforced and not accidentally disabled in any environment that serves real traffic. |
| `HttpOnly` attribute mandatory to prevent JavaScript cookie theft via XSS. | `httpOnly` is set. | **OK.** The encrypted checkout cookie is not accessible to `document.cookie`. |
| `SameSite` should be `Strict` or `Lax`; never `None` without `Secure` or browser defaults. | `sameSite: lax` is used. | **OK for a checkout flow.** `Lax` allows top-level safe cross-site navigation (e.g., return from Stripe redirect or wallet app) while still blocking cross-site POSTs. `Strict` could break legitimate redirects from payment wallets or Stripe. |
| Non-persistent/session cookies preferred for sensitive sessions. | `maxAge: 3600s` (1 hour) is set, so the cookie is persistent for up to an hour. | **Acceptable for a checkout flow**, but the duration should be as short as operationally feasible. |
| Idle, absolute, and renewal timeouts should be enforced server-side. | `iron-session` TTL is 1 hour. The synopsis does not mention an idle vs. absolute timeout distinction. | **Gap to audit:** Confirm whether the 1-hour TTL is absolute from creation or sliding idle. For a checkout session, an **absolute timeout** is preferable because it limits the window for session hijacking regardless of attacker activity. |
| Session ID should be renewed after privilege-level changes. | Not explicitly described. | **Gap to audit:** Starting the checkout (moving from anonymous basket to checkout session), entering address, selecting shipping, and entering payment could be considered privilege/integrity level changes. Consider whether `iron-session` rotates or re-seals the session at those transitions. |
| Clear cookie on completion / logout. | Return handler clears basket, address, shipping on success. | **Partial.** The session cookie itself is not necessarily invalidated; only the checkout data inside it is cleared. The `completedPaymentIntentId` / `lastPaymentIntentId` remain for success-page refresh. This is acceptable for audit/refresh but should be revisited if session fixation is a concern. |

### Bottom line for audit
The cookie configuration (`Secure`, `HttpOnly`, `SameSite=Lax`) matches OWASP baseline expectations. The two areas to investigate in stage 2 are **timeout semantics** (absolute vs. idle) and **session ID / trace ID entropy and rotation** at funnel transitions.

## 3. OWASP CSRF Prevention Cheat Sheet — checkout actions

### Source
- OWASP Cheat Sheet Series, *Cross-Site Request Forgery Prevention Cheat Sheet* (https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

### Findings
OWASP lists the primary CSRF defenses in order of preference:

1. **Synchronizer token pattern** — server-generated token per session or per request, validated on state-changing requests.
2. **Signed double-submit cookie** — HMAC token bound to the session, sent as both cookie and request parameter/header.
3. **Fetch Metadata headers** (`Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`) with fallback to `Origin`/`Referer` verification.
4. **Defense in depth:** `SameSite` cookie attribute and origin-header checks.

### Calibration to this repo
The checkout funnel uses Next.js Server Actions (`saveAddress`, `saveShippingAction`, `initCheckoutSession`) and API routes (`/api/checkout/payment-intent-session`, `/api/checkout/return`). `CHECKOUT-SYNOPSIS.md` notes the checkout cookie is `SameSite: lax` and `HttpOnly`.

| Defense | Current state (per synopsis) | Comment |
|---|---|---|
| Synchronizer / CSRF token | Not described. | **Gap to audit.** Next.js Server Actions are not automatically CSRF-proof against same-site attacks. If a malicious same-site (subdomain) page can call the action, a token is needed. |
| `SameSite=Lax` | Set on checkout cookie. | **Partial defense.** Blocks cross-site POSTs to checkout actions. Does **not** block same-site or top-level GET navigations. |
| Fetch Metadata / origin checks | Not described. | **Gap to audit.** For API routes and server actions that mutate state, `Sec-Fetch-Site` and `Origin` validation should be considered, especially for `/api/checkout/payment-intent-session` and `/api/checkout/return`. |
| `SameSite=None` risk | Not used. | **OK.** `Lax` is correct here. |

### Bottom line for audit
`SameSite=Lax` is a good baseline but is not a complete CSRF strategy by itself. Stage 2 should verify whether Server Actions and the payment-intent/return routes have an additional CSRF signal (token, Fetch Metadata, or origin binding) or whether they rely solely on cookie `SameSite`.

## 4. OWASP Input Validation Cheat Sheet — checkout data

### Source
- OWASP Cheat Sheet Series, *Input Validation Cheat Sheet* (https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

### Findings
OWASP recommends:
- Validate at **syntactic** and **semantic** levels.
- Use **allowlists**, not denylists, as the primary validation strategy.
- Validate **server-side**; client-side validation is for UX only.
- Validate as **early as possible** in the data flow.
- Apply min/max ranges, allowed-value sets, strict regex anchored to the full string (`^...$`), and type conversion with strict exception handling.

### Calibration to this repo
`CHECKOUT-SYNOPSIS.md` shows validation at multiple points:

| Input | Validation described |
|---|---|
| Address | `submitShippingAction` calls Google Address Validation API; accepts only `PREMISE` or `SUB_PREMISE` granularity with `addressComplete=true` and no inferred components; normalizes to `{street, streetNumber, city, postalCode, regionCode}`. |
| Shipping option | `saveShippingAction` validates `priceInCents > 0` and integer. |
| Payment total | Payment-intent route re-derives `grandTotal` from live Sanity; ignores client value. |
| Quantities | Payment page guards `qty ≤ 10`; `enrichedItems` caps at `availableStock`. |
| Email | `createOrderFromPaymentIntent` validates with Zod. |
| Payment-Intent ID in return URL | Return handler verifies `payment_intent` from URL matches `session.paymentIntentId` or `session.completedPaymentIntentId`. |

### Gaps / notes for audit
- **Basket contents:** `session.basket` is `{productId, quantity}[]`. The synopsis does not describe whether `productId` is allow-listed to a known Sanity product ID set server-side before being used in pricing/stock logic. This is the kind of early validation OWASP emphasizes.
- **Compact basket metadata:** The `id:qty,id:qty` string is parsed from PaymentIntent metadata in the webhook path. The parser should strictly validate the format ( anchored regex), reject unexpected characters, and validate that IDs exist in Sanity before order creation.
- **Stripe metadata size guard:** The 500-char limit check is a syntactic/length guard. It aligns with OWASP’s “minimum and maximum length check” recommendation.

### Bottom line
The architecture already performs authoritative price derivation server-side and uses a third-party API for address validation, which matches OWASP’s “validate early, on the server” principle. Stage 2 should focus on whether product IDs, basket compact strings, and webhook payloads are allow-listed/validated before use.

## 5. Stripe webhook signature verification

### Source
- Stripe Docs, *Receive Stripe events in your webhook endpoint* (https://docs.stripe.com/webhooks)
- Stripe Docs, *Resolve webhook signature verification errors* (https://docs.stripe.com/webhooks/signature)

### Findings
Stripe strongly recommends that every webhook endpoint **verify the `Stripe-Signature` header** before acting on the event. The standard pattern is:

1. Read the **raw request body** exactly as received (do not parse/re-stringify it — any manipulation breaks verification).
2. Pass the raw body, the `Stripe-Signature` header, and the endpoint’s `whsec_…` signing secret to `stripe.webhooks.constructEvent()` (or equivalent).
3. If verification fails, return `400` and do not process the event.
4. If verification succeeds, return `2xx` **before** running long-lived logic; long work should be done asynchronously.

### Calibration to this repo
`CHECKOUT-SYNOPSIS.md` §3.6 mentions the webhook path as an **“async safety net”** that also calls `createOrderFromPaymentIntent`. It does **not** describe signature verification in the synopsis.

**Gap to audit:** Stage 2 must confirm that the production webhook handler:
- Uses the raw body (not `req.json()` or a transformed body) for `constructEvent`.
- Has a configured `STRIPE_WEBHOOK_SECRET`.
- Returns `2xx` quickly and does not expose internal errors to Stripe.
- Rejects events whose signature does not verify.

If the webhook handler is not yet verifying signatures, that is a security gap to fix in the audit stage.

## 6. Stripe idempotency

### Source
- Stripe Docs, *Idempotent requests* (https://docs.stripe.com/api/idempotent_requests)

### Findings
- Stripe supports idempotency keys on all `POST` requests.
- A client generates a unique key (Stripe suggests a V4 UUID or another high-entropy random string, up to 255 characters). Avoid sensitive data in the key.
- Stripe saves the result of the first request with that key for at least 24 hours; subsequent requests with the same key return the same result, including `500` errors.
- The idempotency layer compares incoming parameters to the original; if they differ, Stripe returns an error.
- `GET` and `DELETE` are idempotent by definition and do not need a key.

### Calibration to this repo
`CHECKOUT-SYNOPSIS.md` describes two idempotency mechanisms:

1. **PaymentIntent create/update key:** The payment-intent route uses `checkoutSessionId` as the Stripe idempotency key. This is **not a UUID** (it contains a timestamp + random component). If the timestamp is stable within a session and the random component is high entropy, collision risk is low, but it is not the form Stripe recommends. It also carries a timestamp, which is not sensitive but is structured.
2. **Order creation guard:** `createOrderFromPaymentIntent` checks whether an `order` document with the given `paymentIntentId` already exists and skips creation if so. This is an application-level idempotency guard.

| Aspect | Current state | Audit note |
|---|---|---|
| Stripe idempotency key | `checkoutSessionId` reused. | Acceptable if the value is unique per checkout attempt and never reused across different baskets/totals. **Risk:** if the same `checkoutSessionId` is reused after a payment failure with a different `grandTotal`, Stripe may reject because parameters changed. |
| Idempotency duration | Stripe keeps results ≥ 24 hours. | If a customer retries > 24 hours later with the same `checkoutSessionId`, a new PaymentIntent is created. This is expected Stripe behavior. |
| Order creation idempotency | Skip if `paymentIntentId` order exists. | **Good.** Prevents duplicate orders on webhook + synchronous return both firing. |

### Bottom line
The architecture has the right shape (re-use PaymentIntent via a stable key, guard order creation by PI ID). Stage 2 should verify the actual entropy and uniqueness of `checkoutSessionId` and confirm the idempotency key is not accidentally reused across different payment attempts.

## 7. Baseline e-commerce checkout UX expectations

### Sources
- Baymard Institute, *The Checkout UX Guide: Optimizing Your Ecommerce Order Flow* (https://baymard.com/learn/checkout-flow-ux-optimization)
- Nielsen Norman Group, *The Mobile Checkout Experience* (https://www.nngroup.com/articles/mobile-checkout-ux/)

### Scope boundary (mandatory exclusion)
The epic only needs **baseline, “does the funnel complete without failing the customer”** expectations. The following are explicitly **out of scope**: visual design, animations, micro-interactions, micro-copy, brand voice, and UX-score/polish recommendations. Findings below are therefore limited to flow integrity, navigation, and recoverability.

### 7.1 Basket
**Baseline expectation:** The customer can view, edit, and confirm the basket contents before entering checkout, and the transition into checkout does not lose the selected items.

- Provide quick, direct access to the cart (no unnecessary intermediate popups).
- Allow quantity changes and easy removal without forcing “Update” buttons or setting quantity to zero.
- Persist the basket across the transition from `/basket` into `/checkout/address`.

**Calibration:** `CHECKOUT-SYNOPSIS.md` §3.1 describes the basket is hydrated from `localStorage` via Zustand, enriched via SWR, capped to `stock - reservedStock`, and saved into the encrypted `iron-session` by `initCheckoutSession`. This matches the baseline. Audit should confirm that if `initCheckoutSession` fails or the cookie is full, the user is not silently dropped.

### 7.2 Address
**Baseline expectation:** The customer can enter and validate a shipping address without re-typing, and invalid addresses are blocked before proceeding.

- Validate address server-side (or via a trusted API) and reject incomplete/inferred addresses.
- Preserve already-entered data on validation failure.
- Use a single, clear set of fields and defaults where possible.

**Calibration:** `CHECKOUT-SYNOPSIS.md` §3.2 uses Google Address Validation with strict acceptance rules (`PREMISE`/`SUB_PREMISE`, `addressComplete=true`, no inferred components) and normalizes to a fixed schema. The form hydrates from `initialAddress` and on `FIX` returns to the client. This is a strong baseline. Audit should confirm that Google API errors or unavailability do not leave the user stuck or permit unvalidated addresses.

### 7.3 Shipping
**Baseline expectation:** The customer sees accurate, available shipping options derived from the address and basket, and the selected option is preserved.

- Shipping cost must be calculated from real address + parcel data, not hard-coded.
- Selection should be clear and single-choice.
- Changing the address should invalidate stale shipping choices (to avoid wrong rates).

**Calibration:** `CHECKOUT-SYNOPSIS.md` §3.3 fetches live AlleKurier rates based on package aggregation from Sanity parcel data, and `saveAddress` cascades to clear shipping fields. This matches. Audit should confirm the radio selection is accessible and the selected option is correctly saved.

### 7.4 Payment
**Baseline expectation:** The customer sees an accurate total, can pay with a supported method, and payment failures are recoverable without restarting the funnel.

- Total must be derived server-side and be authoritative; do not trust client totals.
- Supported payment methods should be visible before the customer attempts payment.
- Payment errors should be specific and preserve non-sensitive context.
- The flow should support the redirect/return pattern where applicable (BLIK, P24, wallets).

**Calibration:** `CHECKOUT-SYNOPSIS.md` §3.4 re-derives `grandTotal` from live Sanity on the server, creates/updates a PaymentIntent, and uses Stripe Elements for BLIK/P24/Card/Apple Pay/Google Pay. Return handler distinguishes `succeeded`, `requires_payment_method`, `canceled`, and `processing`. This is a solid baseline. Audit should confirm the retry/backoff on `payment-intent-session` does not create duplicate PaymentIntents and that the return URL cannot be replayed with an unrelated PI.

### 7.5 Order confirmation
**Baseline expectation:** After a successful payment, the customer sees a clear confirmation with order reference, amount, items, and next steps; refresh/reload does not break the page.

- Show order number, items, pricing, shipping address, estimated delivery, and payment method.
- Support direct page refresh (e.g., via a `payment_intent` query parameter and fallback order lookup).
- For processing states, offer a non-blocking refresh/polling mechanism.

**Calibration:** `CHECKOUT-SYNOPSIS.md` §3.7 describes a success page that retrieves the PaymentIntent, falls back to `fetchOrderByPaymentIntentId` in Sanity if the session is gone, and shows `OrderDetails` plus a `RefreshButton` for `processing`. This matches the baseline. Audit should confirm the fallback path does not leak another user’s order and that the `completedPaymentIntentId`/`lastPaymentIntentId` check is robust.

## 9. Synthesis / open questions for the audit stage (`sang-logium-4ff.2`)

The following items are flagged for `sang-logium-4ff.2` because they emerged from calibrating external standards against `CHECKOUT-SYNOPSIS.md`:

1. **PCI DSS v4.0.1 script-attack criterion:** Does the merchant page have CSP / script-integrity controls or a documented Stripe-provided assurance for SAQ A eligibility?
2. **Session timeout semantics:** Is the 1-hour `iron-session` TTL absolute or idle? Is the cookie invalidated after checkout completion?
3. **Session / trace ID entropy and rotation:** Is `checkoutSessionId` generated with sufficient entropy, and is the `iron-session` cookie value rotated at funnel transitions?
4. **CSRF beyond `SameSite=Lax`:** Do state-changing Server Actions and API routes have an additional CSRF signal (token, Fetch Metadata, or origin verification)?
5. **Webhook signature verification:** Does the production webhook handler verify `Stripe-Signature` with the raw body?
6. **Idempotency key uniqueness:** Is `checkoutSessionId` never reused across different payment attempts or changed basket totals?
7. **Input allowlisting:** Are product IDs, basket compact strings, and webhook payloads allow-listed / strictly parsed before downstream use?
