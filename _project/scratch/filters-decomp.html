Filters & Sorting — bring to professional level, all locations

One focus only: the filter sidebar and the sort control, everywhere they appear — /products, /products/headphones, /products/accessories, /products/audio-electronics and subcategories. Happy path and edge cases. Success is measured by a human doing a live check in a browser on localhost:3000 — nothing else.

Swept 2026-09-04 · 16 problems collected · source: _project/filters/DECOMP-DRAFT.md

The problem we are solving

Filters and sorting today are uneven. Some things work; several edges break; quality varies by location. Before writing beads issues we want the leanest decomposition that actually reaches a professional-grade experience — no bloated issues, no scaffolding that doesn't move what the end user sees, no solving an invented version of the problem.

Guiding principle

Filters operate on the full inventory in the CMS for the current query context (category + any other active filters) — never on the products currently loaded in the viewport. When a user narrows price or picks a brand they expect to be looking at everything in inventory that matches, not a shrunk slice of what was on screen. Every bound, count and result is the true CMS representation for that context.

Five ways to decompose — ranked

▲ PICK

E — Thin vertical slices, each one observable win, sequenced

One issue = one visible change with a minimal diff. Merges independently, verifiable alone on :3000, banks value if we stop early. The single shared risk — slices disagreeing on the facet-applicability foundation — is killed by making Slice 1 the anchor that decides it once.

#2

B — By mechanism: three coherent epics (Facet Relevance / Price Fidelity / Sidebar Polish)

Each epic is one mental model, one code path, minimal rework, strong UX line. Risk: the Facet Relevance epic is chunky enough that an implementing agent could over-reach. We borrow its epic framing for E.

#3

D — Two-phase: data-model epic, then experience epic

Cleanly separates "is the data right" from "is the presentation right" — genuinely different verification modes. Risk: phase 1 has a thin standalone user-visible outcome, which strains the acceptance-test-as-goal rule.

✗

A — One issue per problem, one flat epic

Cheap to write, but P5/P6/P7/P8 share one root, so four agents touch that path four times. P9 is a phantom. A checklist, not an outcome.

✗

C — By location (one epic per page)

Matches the "each location" phrasing but the facet-relevance and price fixes recur in all four epics — worst duplication and mix-up risk.

Recommended plan — E, organised under two thin epics

Run E's slices. Group them under two small epics for legibility. Slice 1 is a hard sequencing anchor — it makes the "which facets apply to which category" decision once, so slices 2–4 don't fight over it.

Why this mitigates the most risk toward the actual UX target: every issue is a live acceptance test (direct line to :3000, not deferred to an epic) · scope creep is structurally bounded (one visible change, minimal diff) · accept/reject on a single outcome, not a bundle · rework risk contained to one explicit first decision · value banked incrementally — stop after Slice 4 and the sidebar is already far more professional.
EPIC Filters Facet Relevance

Only filters that can do something, ever appear

The facet groups and options shown at any location are exactly what that category's CMS inventory supports.

  1. Category page shows only applicable facet groups anchor
    When I open /products/audio-electronics, then I see only facets that apply to audio electronics — no Wearing style, no Back design, no Driver type.
    covers P5 · establishes the per-category facet-applicability source used by slices 2–4
  2. No zero-count options inside a group
    When I view any filter group, then every option listed would return at least one product.
    covers P6
  3. Drop the redundant Category facet on category pages
    When I'm on /products/headphones, then there is no "Category" filter offering headphones / accessories / audio-electronics.
    covers P7
  4. Neutralise the Compatibility facet until its data is clean
    When I open the filter sidebar anywhere, then I do not see a Compatibility facet full of malformed model strings.
    covers P8 · P9 falls out once this + Slice 1 + P4 land
EPIC Filters Price And Polish

The sidebar reads as finished, and price is precise

Price scale reflects the real distribution for the current context; the sidebar is compact and consistent; sorting and edge paths behave.

  1. Brand list: initial set + progressive "show more"
    When I open a page with many brands, then I see a short list (~7) with a "show more" control, and the sidebar's other filters stay visible.
    covers P4 · blocked by P4-PRE (research)
  2. Price scale absorbs outliers
    When I drag the price slider on /products/headphones, then the range I care about is usable and the $38k outlier no longer squashes it — and that product is still reachable.
    covers P1 + P10 · re-check P2 with the human first
  3. One "Price" heading
    When I look at the price section, then the word "Price" appears once.
    covers P3
  4. Unknown filter values are dropped
    When I load a URL with a bogus ?brand= value, then it is ignored, no phantom chip appears, and I see the unfiltered results.
    covers P11
  5. Out-of-range page corrects the URL
    When I load ?page=999, then I land on the real last page and the URL and pager say so.
    covers P13
  6. One clear-all label + a useful empty state
    When my filters match nothing, then the reset control has the same label as the chips bar and the screen points me at what to loosen.
    covers P14

P12, P15, P16 are check-first — resolve them with a live human pass before deciding whether each becomes a slice here or is dropped. If P12 or P16 turn up a real defect, add a slice; otherwise close as "verified fine".
